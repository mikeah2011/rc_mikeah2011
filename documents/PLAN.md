# API 通知系统实施计划

## 目标与当前决策

接收业务系统已组装好的外部 HTTP(S) 通知请求，持久化后异步投递，并在失败时尽可能恢复。MVP 是最小可行实现阶段，不是系统名称。

本计划按 2026-09-15 的目标收敛更新，替代早期“尚无应用代码”的状态描述。应用已有 Laravel Controller → Service → Repository、通知与尝试记录、Outbox、队列 Job 和人工重投入口。

当前默认 **Outbox + database queue**；本轮不引入 Redis/Horizon、RabbitMQ、Kafka，不推进邮件/短信或多目标广播。完整设计边界及判断依据统一见 [SA/SD](SA_SD.md)。

## 分批交付规则

- 一个批次围绕一个可审阅目标，包含对应实现、必要迁移、回归用例及相关文档，不积累成一次大包提交。
- 行为修复先建立回归场景，再修改代码；不把 Queue fake 或 SQLite 结果当作生产并发保证。
- 只记录实际完成内容，区分实现、验证和上线条件。没有 schema 变化就不为凑批次添加迁移。
- 默认只本地提交，不自动推送远程，不覆盖已有用户修改，不提交 `.env`、凭据或 `vendor/`。

## 本轮批次

| 批次 | 内容 | 验收重点 |
|---|---|---|
| 1. HTTP 可靠投递闭环 | 修复先发布后标记；统一创建/人工重投调度；补齐延迟释放、耗尽失败、轮次隔离、原始 Body 保留 | 数据库真实入队/消费、入队失败保留 Outbox、事务回滚、临时失败后重试、过期任务不投递 |
| 2. 运行配置 | Laravel 13 Scheduler 注册、进程职责、超时关系、共享缓存锁、容器 Worker/Scheduler | 命令能发现定时任务；API、队列、调度器使用一致环境；禁止不可靠队列配置 |
| 3. 设计说明 | 按作业问题整理系统边界、失败语义、未采纳方案及演进依据 | 默认值与实际实现一致，所有未来能力明确标为未完成 |

本轮选择单通知行锁覆盖一次有界 HTTP 请求，加共享缓存锁防止重叠消费；这是易解释的保守实现，但会占用数据库连接和锁。大规模投递前需测量，再考虑更复杂的租约/状态提交设计。

## 后续批次与优先级

| 优先级 | 工作 | 完成标准 |
|---|---|---|
| 上线前 | 调用方鉴权及权限隔离 | 未授权不能创建、读取或重投其他调用方通知 |
| 上线前 | SSRF、出口和凭据保护 | 实际连接受白名单约束，日志脱敏，敏感数据保护，大小与保留期限制 |
| 上线前 | 幂等完整性 | 并发同键冲突可恢复；调用方标识约束明确；人工重投支持独立幂等键 |
| 上线前 | 运行可靠性演练 | PostgreSQL 并发、Worker 被终止、队列不可用和持久化失败有可重复证据 |
| 高 | 查询与对账 | 提供受控状态查询、失败记录查看及队列终止但业务仍 pending 的对账 |
| 高 | 积压与告警 | 未处理数、最旧待处理年龄、队列深度、失败率及数据库锁等待可观测 |
| 按需要 | Outbox 隔离与归档 | 坏记录不长期阻塞后续记录，有失败预算、人工恢复和审计；当前不是完整 DLQ |
| 按负载 | 性能与队列演进 | 先压测与数据库优化，再依据瓶颈选择独立队列/CDC，而不是预先搭平台 |

Email/SMS、多目标广播、管理后台和严格顺序不是本轮交付目标。若后续需求真的需要，先更新边界和验收标准，再独立实施。

## 验收场景

提交后异步投递；同键同内容/不同内容；Outbox 或队列写入失败回滚；入队后标记失败允许重复恢复；HTTP 成功、永久失败、限流、服务器错误、连接失败与预算耗尽；`Retry-After`；不跟随重定向；原始 Body 不变；旧轮次/重复任务不重复已记录的成功；人工重投保留历史并发布新轮次；Scheduler 和 Worker 能实际运行。

供应商成功但本地未保存的窗口仍可能产生重复，验收不能把这个事实隐藏成“恰好一次”。运行操作见 [SETUP](SETUP.md)，队列一致性说明见 [OUTBOX_BROKER](OUTBOX_BROKER.md)。
