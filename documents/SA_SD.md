# 系统分析与设计（SA/SD）

## 设计目标与判断依据

设计并实现一个内部服务，接收业务系统提交的外部 HTTP(S) 通知请求，并尽可能可靠地投递到目标地址。

例如注册后通知广告系统、订阅付款后通知 CRM、购买商品后通知库存系统。这些场景在本服务中都是一次 HTTP 投递，不需要按广告、CRM、库存建立不同的通知渠道。

第一版优先解决持久化、异步投递与失败可恢复的问题，不以渠道数量、架构规模或引入多少中间件作为完成标准。“MVP”表示最小可行实现阶段，不是系统名称。

本文按作业要求回答三个问题：**系统边界、可靠性与失败处理、取舍与演进**。设计保证成立依赖正确的部署配置；尚未完成的保障见文末，不把设计意图等同于已上线能力。

## 1. 系统边界

### 1.1 在本系统中解决什么

| 问题 | 处理方式 | 判断依据 |
|---|---|---|
| 外部 API 地址、Method、Header、Body 不同 | 接收业务方已组装好的请求，保存并按原始 Body 投递 | 差异属于请求数据，不必为每个供应商编写一个驱动 |
| 业务流程不应等待供应商响应 | 通知与投递意图持久化后返回 `202 Accepted`，Worker 异步投递 | 将供应商的响应时间与业务请求耗时解耦 |
| 供应商偶发超时或不可用 | 有限重试、退避、抖动及 `Retry-After` | 提升恢复机会，同时避免故障期间无限重试 |
| 进程退出或入队失败 | 持久化 Outbox、持久化队列及失败记录 | 恢复不依赖当前进程的内存 |
| 失败后需要定位和补救 | 保存尝试记录，对最终失败通知允许人工重投 | 有限自动化必须有明确的失败出口 |
| 调用方因接收响应丢失而重复提交 | 使用调用方标识与提交幂等键识别重复请求 | 重复提交不应无意间创建多条通知；不等于外部业务幂等 |

接收接口返回的是“本服务已接受并保存”，不是“供应商已成功执行”。

### 1.2 明确不在第一版解决什么，为什么

| 不解决的问题 | 责任归属 / 原因 |
|---|---|
| 广告、CRM、库存等业务参数的组装和字段映射 | 业务方了解供应商协议；本服务保持通用投递边界 |
| 动态 OAuth 刷新、供应商 SDK、签名脚本 | 第一版传递调用方提供的请求；复杂适配增加协议和凭据生命周期管理成本 |
| 外部响应 Body 的业务含义 | 默认以 HTTP `2xx` 判断投递成功；`200` 内含业务错误需另行约定适配规则 |
| 业务系统事务提交与本服务接收之间的原子性 | 两个系统不能靠本服务本地事务原子提交；业务侧需要自己的 Outbox 或补偿流程 |
| 外部操作恰好执行一次 | 供应商成功后响应丢失仍可能重试，必须依赖供应商业务幂等 |
| 同一订单或商品的严格事件顺序 | 并发与重试可能改变抵达顺序；有顺序要求时需单独设计分区键、版本检查或串行策略 |
| 邮件、短信、多目标广播、管理后台 | 本次需求是外部 HTTP 请求投递；这些能力不是闭环的必要条件 |
| 无限期重试、保证每条通知最终成功 | 永久错误及长期故障必须可终止，避免无限占用资源 |

尤其是库存扣减、付款状态变更等有副作用的请求，业务方应提供跨自动重试与人工重投都不变的供应商幂等标识，不能把本服务的提交幂等键当作供应商已经去重的证明。

### 1.3 架构与职责

采用 Laravel 单体代码库，API、Outbox 转发器和 Queue Worker 独立运行。默认使用 database queue；生产数据库建议 PostgreSQL，SQLite 用于本地验证。不要求部署 Redis、Horizon、RabbitMQ 或 Kafka。

```text
业务系统（组装 URL / Method / Headers / 原始 Body）
  |
  | POST /api/notifications
  v
Controller -> Service -> Repository
  |
  | 同一数据库事务
  +--> notifications（请求、状态、轮次）
  +--> outbox（待入队的投递意图）
  |
  +--> 提交成功后返回 202 + 通知 ID

Scheduler -> outbox:flush
                 |
                 | 入队成功后再标记 processed_at
                 v
            持久化队列
                 |
                 v
            Queue Worker -> HttpChannel -> 外部 HTTP(S) API
                 |
                 +--> notification_attempts + 通知状态
                 +--> 延迟重试 / 最终失败

人工处理 -> POST /api/notifications/{id}/retry
                 |
                 +--> 新轮次 + 新投递意图（同一事务）
```

Controller 处理协议和响应，Service 处理事务与业务规则，Repository 负责数据访问；Job 管理队列生命周期，HttpChannel 负责 HTTP 调用及结果分类。保留渠道抽象不表示邮件、短信或多目标广播已经实现。

核心数据：

| 数据 | 用途 |
|---|---|
| `notifications` | 原始请求、`pending / delivered / failed` 状态、尝试次数、`delivery_round`、下次尝试时间 |
| `outbox` | 待发布投递意图及 `available_at / processed_at`；已发布不等于已送达 |
| `jobs / failed_jobs` | Laravel database queue 的任务调度、预留及异常失败证据 |
| `notification_attempts` | HTTP 尝试的开始/结束、状态码及脱敏错误；不把完整供应商响应作为业务结果返回 |

## 2. 可靠性与失败处理

### 2.1 选择什么投递语义

选择**允许重复、有限重试的至少一次处理模型**：对于持久化的投递意图，优先允许重复领取和重试，不因进程切换而主动丢弃。它不代表每条通知都一定到达供应商，更不代表外部业务恰好执行一次。

以下窗口无法仅靠本服务消除：供应商已经执行操作，但响应丢失，或者本服务在保存成功状态之前退出。恢复后可能再次投递。因此不宣称 exactly-once；HTTP 成功记录与外部业务提交之间不存在共同事务。

### 2.2 各阶段如何防止静默漏投

| 阶段 / 故障 | 处理原则 |
|---|---|
| 保存通知失败 | 通知与 Outbox 一起回滚，不返回成功接收 |
| 已提交但调用方未收到 `202` | 调用方使用同一提交幂等键重试 |
| Outbox 入队失败 | 保持未处理，命令报错；后续扫描继续尝试，并由运维关注积压 |
| 入队成功、标记 Outbox 前进程退出 | 可能重复发布，但不能先标记已处理再异步发布 |
| 多个转发器竞争同一条记录 | 在事务内重新读取并锁定记录，避免按过期查询结果重复处理 |
| Worker 退出 | 持久化队列的预留超时后可重新领取；受队列执行预算约束 |
| 重复任务、过期轮次任务 | 投递前重新检查状态与轮次；不再次投递已终止的通知或覆盖新轮次 |
| 保存投递结果时数据库失败 | 不吞掉异常或伪装任务成功，保留队列恢复/失败证据 |

同库 database queue 可让入队与 Outbox 标记在一个事务内提交。切换外部 Broker 后无法跨库原子提交，只能采用“发布确认后标记”的至少一次转发策略，接受不确定窗口中的重复。Broker 持久性和确认机制也必须正确配置。

关闭 Outbox 的简化模式仅适用于通知与 database queue 使用同一数据库连接、事务内入队的配置。`afterCommit` 不是防漏投机制：先提交再入队仍有崩溃窗口。

### 2.3 外部系统失败时如何处理

| 结果 | 策略 |
|---|---|
| HTTP `2xx` | 标记 `delivered`，结束本轮 |
| 网络连接失败、超时、HTTP `408 / 429 / 5xx` | 未耗尽预算时延迟重试；耗尽则标记 `failed` |
| 其他 `4xx` | 视为永久失败，不自动重试；由人工核对请求或凭据 |
| HTTP `3xx` | 不自动跟随重定向，标记失败 |
| 程序错误、数据库异常 | 交给队列异常生命周期处理，不当作普通 HTTP 成功返回 |

默认每轮最多 8 次 HTTP 尝试（包含首次），并设置独立的队列执行预算；进程异常可能使实际 HTTP 次数少于预算。退避基线为 10 秒，按指数增长，加少量抖动，上限 3600 秒。合法 `Retry-After` 用于安排重试并受上限约束；非法值退回普通退避。

HTTP 超时必须小于 Job 超时，Job 超时必须小于队列 `retry_after`，避免尚未结束的任务被另一个 Worker 提前领取。HTTP Client 不额外叠加一层自动重试。

### 2.4 长期不可用怎么办

不无限重试，不在 API 请求内等待供应商恢复。自动预算耗尽后进入最终失败，保留通知和历史尝试，由人工排查供应商故障、请求格式或凭据问题。

人工重投仅从 `failed` 开启新轮次，重置本轮尝试计数，并在同一事务中持久化新的投递意图；历史尝试不删除。旧轮次 Job 不得更新或投递新轮次。人工重投不修改原始请求；修正参数时提交新的通知。

上线时需要 Worker 与 Scheduler 进程监管、积压与失败告警，以及故障恢复后的处理流程。供应商不可用时应监控最旧未处理时间，而不只看总条数。若队列异常终止与业务失败状态同步也遇到数据库故障，需要对账恢复；自动对账工具仍属后续工作。

## 3. 取舍与演进

### 3.1 如何判断 AI 建议是否过度

判断标准是：**是否直接解决本次 HTTP 可靠投递需求、是否有实际负载证据、能否解释新增故障模式、团队能否承担运维成本。**

以下是本轮针对已讨论方案的范围收敛，不应写成此前已经由项目负责人逐项否决过的历史事实。

已经明确发生的框架取舍是：AI 曾建议 Python/FastAPI，项目负责人选择熟悉的 PHP/Laravel。不是说 FastAPI 本身过度，而是在本次交付中换用新技术的学习与维护成本缺少足够收益；历史依据见 [技术选型记录](TECH_STACK.md)。

| 已讨论方案 | 本轮选择 | 理由 |
|---|---|---|
| Redis + Horizon 作为默认必需组件 | 不作为第一版前提，保留 database queue 默认值 | 当前没有流量证据证明必须引入新基础设施；已有数据库足够建立闭环 |
| RabbitMQ / Kafka / CDC | 暂不落地 | Broker 本身不能解决业务数据库与消息发布双写；CDC 增加部署、位点及恢复管理成本 |
| 多目标广播、Email/SMS 渠道 | 暂缓，聚焦单请求单 HTTP 目标 | 截图中的广告、CRM、库存都是 HTTP API，不需要不同传输渠道 |
| 独立 `dead_letter` 平台和管理仪表盘 | 暂缓 | 先使用业务 `failed` 状态、尝试记录、Laravel `failed_jobs` 与人工重投；Outbox 发布失败另行保留待处理记录 |
| Outbox 拆到专用数据库 | 不作为直接的扩容手段 | 简单拆库会破坏通知与 Outbox 同事务的关键前提 |
| 为写入性能关闭关键索引 | 不采用 | 唯一约束与查询索引有正确性和可恢复性作用，不应未经测量牺牲它们 |

保留 Outbox 是沿用已存在的事务投递意图与后续队列切换边界，而不是说同库 database queue 必须再加 Outbox。同库事务入队本身也是合理的更简方案；Outbox 会额外增加写入、扫描和调度延迟，应明确承担这份成本。

### 3.2 流量或复杂度上升后如何演进

不预设 QPS 门槛。先建立请求量、投递延迟、最旧待处理年龄、失败率、数据库 I/O、锁等待与队列深度基线，再以实测瓶颈决策。

| 触发证据 | 优先动作 | 进一步演进及代价 |
|---|---|---|
| Outbox 等待时间持续增长 | 检查 Scheduler、转发错误、索引和有界批量；压测并发转发 | 按测量缩短扫描间隔或增加转发器；注意数据库锁与连接压力 |
| 队列积压而数据库仍有余量 | 增加 Worker，调整并发和超时 | 增加吞吐同时可能加大供应商压力，需要配额管理 |
| 队列读写成为主数据库瓶颈 | 清理已终止历史记录，评估索引与存储 | 评估 Redis 或 RabbitMQ；仍保留 Outbox 或等价一致性机制 |
| 单个供应商故障拖累其他目标 | 按供应商隔离队列与并发 | 增加限流、熔断、恢复探测；需要明确公平性与资源预算 |
| 多消费者、事件回放、大规模事件流成为真实需求 | 评估 Kafka + CDC | 引入日志保留、消费位点、重复处理与恢复运维；并非普通 HTTP 队列的无成本替换 |
| 相同业务对象要求顺序 | 引入业务分区键、版本号或串行处理 | 同一分区吞吐降低，失败事件阻塞后续事件的策略需要业务确认 |
| 多个供应商反复出现协议组装需求 | 提取受控供应商适配器 | 纳入签名、鉴权刷新和响应语义；保持与通用投递器分离 |

## 4. 实施范围与上线前条件

本轮优先修复 Outbox 入队窗口、统一投递重试、人工重投事务和旧轮次隔离，并对齐 Laravel 实际 Scheduler 入口。运行方式见 [启动说明](SETUP.md)，转发一致性细节见 [Outbox 与队列](OUTBOX_BROKER.md)，分批安排见 [实施计划](PLAN.md)。

这不等于已可直接生产开放。以下条件须在生产使用前落实或明确接受限制：

- 调用方鉴权及查询/重投权限隔离；请求中的调用方标识本身不是身份认证。
- 目标白名单、实际连接的 SSRF 防护和出口网络限制；仅检查 `http/https` 和禁用重定向不够。
- 凭据加密、日志脱敏、请求/响应大小限制及保留期策略。
- PostgreSQL 并发、进程崩溃和真实 Broker 故障演练；本地 SQLite 结果不能替代这些证据。
- 积压告警、备份恢复、失败对账，以及人工重投接口的独立请求幂等机制。

当前 HTTP 尝试与通知结果在同一事务内提交，进程崩溃或事务失败时，本次尝试记录也可能不存在；不能仅凭“没有尝试记录”断定请求未发出。历史记录会保留，但尝试表暂未单独保存投递轮次，后续审计能力仍需补齐。

**最终判断：第一版应交付可解释、可恢复的 HTTP 投递闭环，而不是宣称不丢失、不重复、无限可用的通用消息平台。**
