# README 调整策略（谁能改、改哪些内容、记录要求）

目的：确保 README.md 保持为项目核心介绍与快速上手文档，而不是用于存放大量的决策历史或第三方官方文档摘录。README 应便于新开发者/运维快速理解如何运行、测试与贡献。

规则：
1. 内容范围
   - 必须包含：项目简介、MVP 范围、快速启动步骤（dev 与 container）、主要 API 列表、关键文档索引（CHANGELOG.md、plan.md、TECH_STACK.md、AI_MODEL_POLICY.md、SETUP.md）、许可证与贡献入门。
   - 不应包含：详细的决策记录（commit 级别历史）、长篇第三方文档复制粘贴、或过长的背景讨论。
   - 深度内容（变更历史、策略讨论、AI 建议记录）应放在专门文档（CHANGELOG.md、TECH_STACK.md、AI_USAGE.md）中并在 README 中索引。

2. 编辑与审阅流程
   - 任何人可以发起 README 修改的 Pull Request（或本地提交），但包含策略/架构变更时必须同时更新相关专用文档并在 CHANGELOG.md 中记录摘要。
   - 自动化/AI 提交：AI 可以草拟 README 修改，但最终合并需人工审阅与批准。任何由 AI 引入的设计改变都需在 TECH_STACK.md 或 AI_USAGE.md 中记录是否采纳及原因。

3. 变更记录要求
   - 每次 README 的重要改动（例如替换技术栈、变更运行流程）应在 CHANGELOG.md 记录一条简短条目：谁、何时、为何、主要影响。
   - 小的修正（错别字、格式、链接修复）只需在提交信息中说明，不必写入 CHANGELOG.md，除非影响运行或策略。

4. 频率与回退
   - README 的内容应随功能演进定期更新（典型节奏：每个里程碑或每次重要迁移后）。
   - 所有变更通过 Git 管理，可通过 git revert 回退。

5. 可视化/本地化
   - README 保持英文/中文并存的关键段（项目简介、快速开始）；长文档可以放在 docs/ 或本地化子文件中。
